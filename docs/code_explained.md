# IPS 코드 원리 (1·2단계)

코드를 **왜 이렇게 짰는지**를 짧게 정리한 문서다. "무엇을 하는가"보다 "왜 그렇게 했나"에 초점을 둔다.

## 큰 그림

리눅스 NFQUEUE로 들어오는 패킷을 하나씩 가로채서 검사한다.

- **1단계**: 받아서 5-튜플(출발지·목적지 IP/포트, 프로토콜)을 읽고 로그만 남긴다. 아직 다 통과. → 관찰(IDS)
- **2단계**: 통계를 쌓아 포트 스캔·SYN 플러드를 벌이는 IP를 일정 시간 차단한다. → 대응(IPS)

패킷마다 `on_packet`이 불리고, 그 반환값(통과/차단)이 곧 커널에 주는 판정이다.

---

## 1단계 — 받아서 읽기

**왜 NFQUEUE인가**
패킷을 커널에서 우리 코드(유저공간)로 넘겨받아 통과/폐기를 직접 정할 수 있다. 인라인 차단의 표준 방식이고, 특징 추출을 마음대로 짤 수 있어 나중에 AI를 붙이기 좋다.

**왜 C API를 클래스로 감쌌나 (`PacketSource`)**
libnetfilter_queue는 C 라이브러리라 열고 닫기를 손으로 짝맞춰야 한다. 클래스로 감싸면 `open()`/`close()`가 짝을 이루고, 소멸자가 안전망으로 `close()`를 부른다. 핸들을 두 객체가 나눠 가지면 두 번 닫는 사고가 나므로 복사도 막았다.

**왜 콜백을 try/catch로 감쌌나**
NFQUEUE는 우리 함수를 C 코드 안에서 부른다. 여기서 C++ 예외가 터져 C 스택을 뚫고 나가면 정의되지 않은 동작(크래시)이다. 그래서 예외를 여기서 잡고, 무슨 일이 있어도 판정은 반드시 돌려준다. 안 그러면 그 패킷이 커널 큐에 영원히 남는다.

**왜 종료를 원자 플래그 + 1초 타임아웃으로 처리하나**
Ctrl+C를 누르면 수신을 멈추고 자원을 정리해야 한다. 시그널 핸들러에서 건드릴 수 있게 종료 플래그를 원자값으로 뒀고, `recv`에 1초 타임아웃을 걸어 패킷이 없어도 주기적으로 깨어나 종료 요청을 확인한다.

**왜 파서가 길이를 다 검사하나 (`PacketParser`)**
입력은 네트워크에서 온 믿을 수 없는 바이트인데 우리는 root로 돈다. 헤더보다 짧은 패킷을 검사 없이 읽으면 버퍼 밖을 읽는다. 그래서 매 단계 길이를 확인하고, IP 헤더 길이도 고정이 아니라 `ihl` 값으로 계산해 전송 헤더 위치를 잡는다.

**왜 IP를 숫자(uint32)로 저장하나 (`FiveTuple`)**
비교·해시 조회가 빠르다. 사람이 읽는 문자열은 로그 찍을 때만 만든다.

## 2단계 — 판단해서 차단하기

### 가장 중요 — 판정 순서 (`on_packet`)

```
파싱 실패        → 통과
화이트리스트     → 통과   (맨 먼저)
차단 목록에 있음 → 폐기
포트 없음        → 통과
통계 상한 초과   → 통과
규칙 위반        → 차단
그 외            → 통과
```

이 **순서 자체가 설계**다.

- **화이트리스트가 맨 앞**: 관리자·게이트웨이·DNS는 무슨 일이 있어도 막으면 안 된다. 오탐으로 막으면 내가 내 서버에서 쫓겨나거나 네트워크가 죽는다. 그래서 어떤 판단보다 먼저 통과.
- **차단 검사가 포트 검사보다 앞**: 이미 차단된 IP가 ICMP처럼 포트 없는 패킷으로 바꿔 빠져나가는 걸 막는다.
- **모르면 통과(fail-open)**: 이 프로젝트에서 제일 무서운 건 정상 서비스를 잘못 막는 거다. 판단 못 하는 패킷은 막기보다 통과가 안전하다.

### 나머지 핵심 결정

**왜 출발지 IP 단위로 세나 (`FlowManager` / `SourceStats`)**
포트 스캔은 한 IP가 여러 포트를 훑는 행위다. 연결 하나만 보면 안 잡힌다. 그래서 IP별로 "최근에 건드린 포트 수"와 "SYN 보낸 횟수"를 센다.

**왜 고정 창(10초마다 리셋)인가**
슬라이딩 창은 더 정밀하지만 자료구조가 무겁다. 규칙 2개엔 과하다. 대신 아주 느린 스캔은 놓칠 수 있는데, 그건 3단계 AI가 맡는다.

**왜 차단 목록을 map + 힙 + 지연삭제로 짰나 (`BlockList`)**
- "이 IP 차단됐나?"는 자주 물으니 map으로 O(1).
- 만료된 걸 정리할 때 전체를 훑으면 느리다. 만료 시각 순 힙을 둬서 맨 위만 보면 된다.
- TTL을 연장하면 힙에 옛날 항목이 남는다. 힙에서 직접 지우는 건 비싸니, 꺼낼 때 map과 대조해 옛날 거면 버린다(지연 삭제).

**왜 규칙을 상속 구조로 짰나 (`Rule`)**
새 공격 유형(예: UDP 스캔)을 추가할 때 기존 코드는 안 건드리고 규칙 클래스 하나만 붙이면 된다.

**왜 통계 맵에 상한을 두나 (`MAX_SOURCES` 등)**
공격자가 출발지 IP를 마구 바꿔 쏘면 맵이 무한히 커져 센서가 메모리로 죽는다. 상한으로 그걸 막는다.

**왜 시간(now)을 인자로 받나**
TTL 만료·창 리셋 같은 시간 로직을 테스트하려면 실제로 10분을 기다릴 순 없다. 시간을 밖에서 넣어주면 테스트에서 시계를 마음대로 돌릴 수 있다.

**왜 스레드 없이 도나**
판정이 해시 조회 몇 번이라 패킷 경로에서 바로 해도 빠르다. 만료 정리도 수신 루프에서 1초마다 같이 한다. 스레드가 없으니 락도 없고 단순하다.

---

## 관통하는 원칙 두 개

- **오탐이 제일 무섭다**: 그래서 fail-open, 화이트리스트 최우선, 차단에 TTL(자동 해제)을 둔다. 잘못 막아도 시간 지나면 풀린다.
- **믿을 수 없는 입력을 root로 다룬다**: 그래서 파서는 모든 길이를 검사하고, C 콜백 경계에서 예외를 막는다.
