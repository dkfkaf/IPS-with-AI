# AI 기반 인라인 IPS 설계 문서

> 졸업 작품 설계서 · 검토용
> 작성: 사이버보안학과 22학번 강원찬

> 현재 IPv4·schema 1 구현의 개념 설명이다. DNS·HTTP·TLS·IPv6 등의 추가 범위는
> [확장 설계](../superpowers/specs/2026-09-01-suricata-inspired-expansion-design.md),
> 정책의 현재/확장 구분은 [핵심 정책 보완](../superpowers/specs/2026-09-12-core-policy-clarification-design.md)을 따른다.

---

## 1. 개요

Rule로 확인된 악성 패킷은 실시간으로 차단하고, AI 이상 판정은 알림과 함께 **판정 적용 이후 동일 출발지 IP의 수신 패킷**을 차단하는 **인라인(inline) 방식의 침입 방지 시스템(IPS)** 을 개발한다. IP 단위 정책이므로 새 연결과 기존 연결 모두 영향받는다.

기존 룰(rule) 기반 보안 장비가 탐지하기 어려운 이상 트래픽을 AI로 판별한다. Rule 판정은 패킷이 목적지에 도달하기 전에 차단하고, AI 판정은 비동기 알림과 이후 접근 차단으로 대응한다.

핵심 설계 원칙은 **"성능이 중요한 패킷 처리부는 C++, 유연한 판단이 필요한 분석부는 Python"** 이라는 역할 분담이다.

---

## 2. 목표와 단계별 개발 계획

인라인 방식은 난이도가 높으므로, 단계별로 완성 가능한 결과물이 나오도록 계획한다. 각 단계가 그 자체로 유의미한 성과가 되어, 최종 목표에 도달하지 못하더라도 앞 단계까지를 결과물로 제출할 수 있다.

| 단계 | 목표 | 완성 시 결과물 |
| --- | --- | --- |
| 1단계 | 패킷 캡처·파싱 | 5-튜플 관찰 |
| 2단계 | Rule 기반 탐지·차단 | 대응형 인라인 IPS |
| 3단계 | AI 연동·이상 알림·판정 이후 수신 패킷 차단 | 하이브리드 IPS |
| 검증 | 가상환경에서 공격 시뮬레이션 | 탐지율·처리 지연 측정 결과 |

## 3. 시스템 아키텍처

지도교수 피드백(실시간 처리 지연 문제)을 반영하여, 모든 패킷을 AI로 검사하지 않는 **하이브리드 구조**로 설계한다.

### 3.1 전체 흐름

```text
INPUT·OUTPUT → C++ 방향별 정책·Flow 통계 → 패킷 verdict 반환
                           │
                 Flow 종료·통계 타임아웃
                           │ 제출 조건 확인
                           ▼
                    비동기 Python AI
                           │ 이상 결과
                           ▼
             C++ 결과 검증·화이트리스트 재확인
                           │
                  출발지 IP TTL 등록 + Qt 알림
                           │
                  이후 해당 IP의 INPUT DROP
```

### 3.2 동작 방식

1. 패킷이 NFQUEUE를 통해 C++ 처리 모듈로 진입한다.
2. 패킷을 **플로우(flow) 단위**로 조립한다. 플로우 식별은 5-튜플(출발지 IP, 목적지 IP, 출발지 포트, 목적지 포트, 프로토콜) 기준으로 하고, 통계적 특징으로 판단한다.
3. 빠른 **1차 Rule 검사**가 대부분의 트래픽을 인라인 경로에서 즉시 처리한다(통과/폐기).
4. 종료·타임아웃된 원격 시작 Flow 중 화이트리스트·차단 IP·1패킷 Flow를 제외하고 특징 벡터를
   **Python AI 엔진으로 비동기 전달**한다. 별도의 ‘애매함’ 분류기는 없다.
5. AI가 이상으로 판정하면 현재 플로우는 탐지 이벤트로 기록·표시하고, 출발지 IP를 TTL 차단 목록에 등록한다. 이후 그 IP의 패킷은 빠른 경로에서 DROP한다.

AI 판정으로 이미 전달한 패킷을 되돌릴 수는 없다. 다만 통계 타임아웃은 실제 연결 종료와 다르며,
IP 차단 적용 이후에는 기존 연결의 수신 패킷도 차단된다. 패킷 verdict는 AI 응답을 기다리지 않는다.

AI의 메시지 계약, 장애 시 fail-open, 과부하 처리, 구현 범위와 성능 검증 기록 형식은 `online_inference.md`에서 정의한다.

## 4. 구성 요소

### 4.1 패킷 처리 모듈 (C++)

- 리눅스 Netfilter의 **NFQUEUE**(`libnetfilter_queue`)로 통과 패킷을 사용자 공간으로 가져온다.
- NFQUEUE가 넘겨준 원시 패킷 바이트에서 **표준 헤더(`<netinet/ip.h>`, `<netinet/tcp.h>` 등)를 직접 파싱**하여 5-튜플을 추출한다. (별도 파싱 라이브러리 미사용)
- 패킷을 플로우 단위로 조립하고 통계적 특징(feature)을 추출한다.
- Rule 1차 검사를 수행하고, verdict(ACCEPT / DROP)를 반환한다.
- 종료·타임아웃된 플로우의 특징 벡터를 **ZeroMQ(cppzmq)** 로 AI 엔진에 전달한다. 데이터는 **JSON(nlohmann/json)** 으로 직렬화한다.

### 4.2 AI 분석 엔진 (Python)

- **오토인코더(autoencoder)** 기반 이상 탐지 모델을 사용한다. 정상 트래픽만 학습시켜 복원 오차가 큰 플로우를 이상으로 판정한다. 학습하지 않은 공격을 탐지할 가능성이 있지만 보장하지 않으며, 공격 종류별 탐지율과 정상 오탐률로 검증한다.
- 학습 데이터셋은 **CICIDS2017** 을 사용한다. 플로우 단위 특징으로 구성되어 본 아키텍처(플로우 단위 분석)와 부합한다.
- ZeroMQ로 특징 벡터를 수신(pyzmq)하고, 판정 결과(정상/이상·점수·임계값·모델 버전)를 센서에 반환한다. 출발지 IP는 응답에 넣지 않고 C++가 보관한 원본 Flow에서만 가져온다.

### 4.3 상태·알림 UI (Qt5)

- C++ 센서와 통합된 시스템 트레이로 구현한다. 웹 서버나 별도 dashboard는 두지 않는다.
- 회색·초록·노랑 아이콘으로 AI 시작/온라인/Rule-only 상태를 표시한다.
- 신규 AI 차단과 최종 AI 오프라인을 알리고, 메뉴에서 누적 통계를 읽거나 프로그램을 종료한다.
- 이벤트 이력, 설정 변경, 화이트리스트 편집, 원격 관리는 졸업작품 범위 밖이다.

## 5. 차단 메커니즘

지도교수가 제안한 세 가지 방식을 조사한 결과, **1차 구현은 NFQUEUE 기반**으로 진행한다.

| 방식 | 특징 | 난이도 | 본 과제 채택 |
| --- | --- | --- | --- |
| iptables | 명령어로 IP를 차단 목록에 추가. 사후 대응형 | 낮음 | 보조 (룰 적용에 부분 활용 가능) |
| **NFQUEUE** | 패킷을 사용자 공간(C++)으로 넘겨 통과/폐기 결정. 인라인 IPS 표준 방식 | 중간 | **1차 구현 (채택)** |
| eBPF / XDP | 커널 공간에서 초고속 처리. 성능 최고 | 높음 | 향후 성능 최적화 과제 |

**채택 근거**: NFQUEUE는 특징 추출을 사용자 공간에서 자유롭게 구현할 수 있어 본 과제의 하이브리드 구조에 적합하다. eBPF/XDP는 성능 이점이 크지만 커널 공간 개발의 난이도(verifier 제약, 디버깅 위험)를 고려하여 향후 과제로 남긴다.

## 6. 오탐(False Positive) 대책

인라인 IPS에서 오탐은 정상 서비스 차단으로 직결되며, 특히 오토인코더 기반 이상 탐지는 정상이지만 평소와 다른 트래픽을 이상으로 판정할 여지가 있어 안전장치가 필수적이다. 두 가지 장치를 둔다.

### 6.1 화이트리스트

- 특정 IP는 Rule·AI 판정 여부와 무관하게 항상 통과시킨다. **모든 차단 판단 이전에** 검사한다.
- 보호 대상: 관리자 접속 IP(개발 중 자기 접속을 스스로 차단하는 사고 방지), 게이트웨이, DNS 서버 등 마비 시 네트워크 전체에 영향을 주는 필수 IP.
- 구현: `config.json`의 `whitelist` 배열로 관리하여 재빌드 없이 IP를 추가한다. 메모리에는 해시셋으로 올려 O(1) 조회한다.
- 현재는 Flow 관찰도 생략한다. 확장 권장안은 새 L7 관찰·알림을 유지하면서 실제 차단만 면제하며,
  이 변경은 아직 구현되지 않았다.

### 6.2 차단 TTL (자동 해제)

- 차단에 유효기간(TTL, 예: 10분)을 두어, 오탐일 경우 시간이 지나면 자동 해제되도록 한다. 실제 공격이면 재차단되므로 보안성은 유지된다.
- 구현: **map + min-heap(우선순위 큐)** 을 함께 사용한다.
  - `map` (IP → 만료 시각): "차단됐나?"를 O(1)로 조회하는 진실의 원천.
  - `min-heap` (만료 시각 순 정렬): 정리 시 전체를 스캔하지 않고 맨 위(가장 빨리 만료될 항목)만 확인.
  - **지연 삭제(lazy deletion)**: 힙에서 꺼낸 항목의 만료 시각을 map의 값과 대조하여, 일치할 때만 실제 해제한다. TTL 연장으로 생긴 낡은(stale) 힙 항목은 대조 시 버린다.
- 데모 규모에서는 단순 map + 주기적 스캔으로도 충분하나, 차단 IP가 대규모로 늘어날 경우를 대비해 min-heap 방식을 채택한다.

## 7. 테스트 및 검증 계획

- **환경**: 가상머신(VM)으로 공격자 VM(예: Kali Linux)과 방어 VM(IPS)을 격리 구성한다.
- **공격 시뮬레이션**: 포트 스캔(nmap), DDoS(hping3 등)로 Rule 기반 실시간 차단을 확인한다. AI는 이상 이벤트 이후 같은 IP의 새 연결 및 기존 연결 수신 패킷이 TTL 동안 차단되는지 확인한다.
- **측정 지표**: 탐지율(정탐/오탐), 처리 지연(latency), 처리량(throughput). TTL 값에 따른 오탐률·보안성 트레이드오프도 실험 대상으로 삼는다.
- **기록 항목**: VM 사양·커널·NFQUEUE 설정·IPS/모델 버전·공격 전송률·반복 횟수·큐 드롭 수를 결과와 함께 기록한다. AI 장애·응답 지연·대기열 포화에서도 Rule 처리가 지속되는지 별도로 검증한다.
- **주의**: 공격 도구는 반드시 격리된 가상환경에서만 실행한다.

## 8. 기술 스택 및 라이브러리

| 역할 | 선택 | 비고 |
| --- | --- | --- |
| 패킷 가로채기 | libnetfilter_queue (NFQUEUE) | 인라인 차단 |

| 로깅 | glog | |

| 단위 테스트 | Google Test·Python unittest | 테스트 코드 존재, 실행 결과와 VM 검증은 별도 기록 |

## 9. 향후 검토 / 확장 사항

- **C++↔Python 통신 형식**: 초기에는 JSON을 사용하되, 성능이 필요해지면 MessagePack 등 바이너리 형식으로 전환 검토.
- **AI 2차 탐지 보강**: 오토인코더(비지도) 완성 후 여유가 되면 지도학습 모델(랜덤포레스트/XGBoost)을 결합해 알려진 공격 정탐률을 높이는 이중 탐지 구조 검토.
- **차단 메커니즘 고도화**: 성능 최적화가 필요할 경우 eBPF/XDP로의 이전 검토.
- **화이트리스트 hot reload**: 실행 중 설정 파일 변경을 자동 반영하는 기능(부가).
