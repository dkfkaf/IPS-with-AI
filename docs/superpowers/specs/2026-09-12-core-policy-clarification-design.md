# 핵심 정책 보완 — 차단 범위·로컬 통신·화이트리스트·캡처 입력

## 1. 문서의 역할

2026-09-12 코드 확인 결과와, DNS부터 확장할 때 적용할 권장 설계를 구분한다.
이번 변경은 문서만 수정한다. 아래의 확장 설계가 현재 프로그램에 구현됐다는 뜻은 아니다.

상위 범위는 [Suricata 장점 확장 설계](2026-09-01-suricata-inspired-expansion-design.md)다.
그 문서의 차단·관찰·AI 대상·캡처 입력에 모호함이 있으면 이 보완 문서를 먼저 따른다.
현재 schema 1의 세부 계약은 [온라인 AI 설계](2026-08-28-online-ai-tray-design.md)를 유지한다.

| --- | --- | --- |
| AI 차단 | 판정 적용 이후 해당 출발지 IP의 수신 패킷 차단 | 이 의미 유지. 새 연결만 차단한다고 표현하지 않음 |

## 2. AI가 차단하는 정확한 범위

### 2.1 현재 동작을 유지한다

AI는 종료 또는 타임아웃된 Flow의 통계를 뒤늦게 받는다. 따라서 **이미 전달한 패킷을 취소하지
못한다.** 이상 결과를 캡처 스레드가 적용하면 출발지 IP를 차단 목록에 넣는다. 그 순간 이후
해당 IP에서 방어 호스트로 들어오는 패킷을 TTL 동안 차단한다.

차단 목록은 IP 단위다. 포트나 개별 연결을 구분하지 않으므로 **새 연결뿐 아니라 이미 진행 중인
다른 연결의 수신 패킷도 영향받는다.** 타임아웃으로 통계가 방출됐지만 실제 통신이 계속되는
연결도 마찬가지다. OUTPUT 패킷 자체는 기존 정책대로 통과한다.

예를 들어 공격자 A의 연결 1에서 이상이 발견됐을 때 연결 2가 이미 열려 있어도, 차단 적용
이후 A가 연결 2로 보내는 패킷은 차단된다. A가 새로 만드는 연결 3도 차단된다. 단, A에게서
이미 받은 데이터까지 없어지는 것은 아니다.

문서·발표·UI에서는 이를 **“AI 이상 알림 + 판정 적용 이후 출발지 IP의 수신 패킷 TTL 차단”**으로
표현한다. “다음 Flow만 차단” 또는 “기존 연결은 계속 허용”이라고 설명하지 않는다. 정말 새
Flow만 막으려면 차단 시점의 기존 연결 집합을 별도로 관리해야 하므로 이번 문서 정정과 다르다.

### 2.2 기존 안전 조건

- Rule과 AI는 기존 `block_ttl_seconds`를 공유한다. AI 신규 차단의 TTL은 결과 적용 시점부터 센다.
- 결과 적용 시 현재 화이트리스트와 차단 목록을 다시 확인한다. 이미 차단된 IP의 중복 AI 결과는
  TTL을 연장하거나 신규 차단 팝업을 반복하지 않는다.
- 차단 IP는 C++가 보관한 원본 Flow에서 가져온다. Python 응답이 차단 대상을 지정하지 않는다.
- 잘못된 응답·AI 장애·AI 큐 포화로 새 AI 차단을 만들지 않는다. 기존 Rule·TTL 차단은 계속한다.
- IP를 공유하는 NAT 사용자와 공유 서버까지 영향받을 수 있다. TTL과 화이트리스트는 이를
  완화할 뿐, 정상 통신의 무중단을 보장하지 않는다.

## 3. 로컬에서 시작한 DNS·HTTP·TLS 통신

### 3.1 왜 현재 방식만으로는 부족한가

방어 호스트가 DNS 서버에 질문하면 첫 패킷은 OUTPUT이다. 현재 코드는 이 Flow를
`LOCAL_INITIATED`로 기록한 뒤, 종료 시 AI 요청에서 제외한다. DNS parser만 추가해도 이 선별
조건을 바꾸지 않으면 로컬에서 시작한 DNS 통신은 AI까지 전달되지 않는다.

`FlowOrigin`은 “연결의 진짜 시작을 증명한 값”이 아니라 **센서가 처음 관찰한 방향**이다.
센서가 연결 중간에 켜지면 실제 시작 방향과 다를 수 있다. 이 한계도 검증 결과에 남긴다.

### 3.2 분석과 차단을 분리하는 권장안

| Flow 종류 | 기존 27개 특징 모델 | 선택적 프로토콜 모델 | AI 이상 시 대응 |
| --- | --- | --- | --- |
| 원격 시작, 비화이트리스트 IPv4 | 기존 제출 조건 충족 시 사용 | 호환되는 관찰 자료가 있으면 사용 | 알림 + 원격 출발지 IP 수신 차단 |
| 로컬 시작 | 보내지 않음 | 해당 시작 방향까지 검증된 모델에만 제출 | 알림만 제공, IP 자동 차단 없음 |
| 화이트리스트 상대와의 통신 | 기존 제외 정책 유지 | 호환되는 관찰 자료가 있으면 사용 | 기록·알림만 제공, 차단 면제 |
| 방향 불명·미지원 입력 | 보내지 않음 | 보내지 않음 | 분석 제외 이유 기록, AI 자동 차단 없음 |

모델이 없거나 비활성이라면 parser·Rule·관찰 기록까지만 동작한다. DNS 기능을 구현했다는
이유만으로 DNS AI 모델도 준비됐다고 표시하지 않는다. IPv6는 확장 설계 17.2의 별도 검증
조건도 충족해야 한다.

로컬 DNS 질문에 이상이 있어도 DNS 서버가 공격자라는 뜻은 아니다. DNS 응답 속 IP나 HTTP의
Host·TLS의 SNI 역시 자동 차단 대상으로 바꿔 쓰지 않는다. 따라서 첫 확장에서는 로컬 시작
통신의 AI 결과로 로컬 IP, DNS 서버 IP, 응답 속 IP 어느 것도 자동 차단하지 않는다.

이 정책은 AI에만 적용한다. 명시적인 outbound Rule 차단은 기존 확장 설계의
`allow_outbound_drop=true`와 `direction=outbound` 조건을 그대로 따른다.

### 3.3 schema 2에서 필요한 문맥

schema 1과 기존 모델의 27개 특징 순서·단위는 바꾸지 않는다. schema 2의 `flow`에 다음 문맥을
추가하고, 원본 `FlowRecord`에도 보관한다.

- `origin`: `remote_initiated` 또는 `local_initiated`.
- `local_ip`, `remote_ip`: INPUT·OUTPUT 방향에서 확인한 방어 호스트와 상대 주소.
- `src_ip`·`dst_ip`: 기존 Flow key 방향을 유지한다. 로컬 시작이면 `src_ip`가 로컬 주소다.

C++와 Python은 주소·origin의 일관성을 검증한다. 원격 시작이면 `remote_ip == src_ip`, 로컬
시작이면 `local_ip == src_ip`여야 한다. 역방향 패킷 때문에 저장된 origin을 뒤집지 않는다.
PCAP에서는 호스트 주소를 명시한 fixture 문맥으로 방향을 결정하며 포트 번호로 추측하지 않는다.

`requested_models`에는 시작 방향·IP version·관찰 schema가 지원되는 모델만 넣는다. 모델
metadata에 `supported_flow_origins`를 두며, 이 필드가 없는 기존 모델은 원격 시작 전용으로
취급한다. Python도 같은 조건을 재검증한다. 로컬 통계를 기존 Flow 모델에 몰래 넣거나, 없어진
프로토콜 필드를 0으로 채우지 않는다.

C++는 결과 적용 시 원본 origin과 현재 화이트리스트를 다시 검사한다. `aggregate_anomaly=true`는
“이상 탐지”이지 “무조건 IP 차단” 명령이 아니다. schema 1만 연결된 동안은 기존 원격 Flow 경로를
유지하고, schema 2와 새 이벤트 경로가 준비되기 전에는 로컬 Flow를 제출하지 않는다.

## 4. 화이트리스트는 차단 면제와 관찰 제외를 구분한다

### 4.1 현재 동작

현재 INPUT의 출발지 또는 OUTPUT의 목적지가 화이트리스트면 즉시 ACCEPT한다. Flow 통계와
AI 분석도 건너뛴다. 관리용 IP를 안전하게 통과시키는 데는 간단하지만, DNS 서버를 등록하면
그 서버와 주고받는 DNS 내용을 새 parser가 볼 기회까지 잃는다.

### 4.2 확장 권장안

화이트리스트는 **상대 IP의 실제 차단을 면제하는 정책**으로 유지하되, L7 관찰을 생략하는
조건으로 사용하지 않는다. INPUT은 source, OUTPUT은 destination을 상대 IP로 판별한다.
로컬 주소가 설정에 있다는 이유로 모든 상대의 통신을 면제해서는 안 된다.

1. 패킷 방향·상대 IP와 화이트리스트 여부를 확인한다.
2. 화이트리스트 상대는 기존 IP 기반 포트 스캔·SYN Flood 누적/차단 및 기존 Flow AI에서 제외한다.
3. 새 DNS·HTTP·TLS 경로는 자원 상한 안에서 양방향 Flow와 관찰 자료를 만든다.
4. 새 L7 Rule이 적중해도 실제 verdict는 ACCEPT다. 이벤트에는 적중 Rule, 원래 action,
   실제 action, `suppressed_by=whitelist`를 기록한다.
5. 선택적 프로토콜 AI가 이상을 반환하면 기록·알림만 제공한다. 결과 적용 시에도 면제를 재검사한다.

화이트리스트도 parser·재조립·이벤트 큐 상한을 초과할 수 있다. 이때 관찰 자료를 버리고 손실을
기록하되, 자원 부족만으로 면제 패킷을 차단하지 않는다. 패킷마다 팝업을 띄우지 않고 Qt는
Flow별 AI 결과를 요약하며, 이벤트 큐 포화 시 기존 비차단 손실 정책을 따른다.

화이트리스트가 아닌 기존 차단 IP는 계속 빠른 경로에서 DROP하고 무거운 분석을 생략한다.
이 설계는 기존 `whitelist`를 확장하는 것이며, 별도의 사용자 관리 목록이나 GUI 편집기를
추가하지 않는다. 구현 때 조기 return 위치를 바꾸고 회귀 테스트로 기존 차단 면제를 확인해야 한다.

## 5. DNS 전에 마련할 패킷 입력 계약

### 5.1 현재 128바이트의 한계

현재 `PacketSource`는 `MAX_COPY_BYTES = 128`로 IP 패킷 앞부분만 사용자 공간에 복사한다.
`ParsedPacket`에는 길이·5-튜플·TCP flag가 있지만 L7 parser가 읽을 payload view는 없다.
긴 DNS 이름이나 TCP 데이터는 중간에서 잘리므로 parser 추가만으로 전체 메시지를 분석할 수 없다.

### 5.2 전체 복사 요청과 잘림 검증

기존 헤더·Flow 통계 전용 모드에서는 128바이트 설정을 유지한다. DNS 등 payload 분석 기능을
켜면 NFQUEUE copy range를 `0xffff`로 요청하고, 사용자 공간 수신 버퍼도 함께 확대한다.
일반 IP 패킷과 netlink metadata를 담도록 수신 버퍼 상한의 초기값은 128 KiB로 둔다.

“전체 복사 요청”은 “모든 패킷이 반드시 온전히 도착함”을 뜻하지 않는다. netlink payload
attribute의 크기 제한은 65,531바이트이며, 원래 크기(`NFQA_CAP_LEN`)와 실제 수신 payload 길이를
비교해야 한다. GSO/offload 패킷을 무조건 일반 MTU 크기로 가정하지 않는다.
이 제한은 [libnetfilter_queue 문서](https://www.netfilter.org/projects/libnetfilter_queue/doxygen/html/group__Queue.html)에 근거한다.

- `recvmsg`의 `MSG_TRUNC`, netlink message 길이, 실제 payload 길이를 검사한다.
- IP·TCP·UDP가 주장하는 길이와 실제로 읽을 수 있는 길이를 분리한다. header의 길이만 믿고
  payload를 읽지 않는다. 기존 27개 특징의 길이 정의도 임의로 바꾸지 않는다.
- PCAP에서도 `caplen`과 원래 packet 길이를 구분한다. 잘린 PCAP를 정상 전체 패킷으로 다루지 않는다.
- 잘림이 있는 DNS datagram은 완성 observation으로 내보내지 않는다. TCP stream에 빠진 bytes가
  있으면 불완전 상태를 전달하고, 재조립이 완성됐다고 표시하지 않는다.
- L7 기능을 켰는데 필요한 복사·버퍼 구성을 적용할 수 없으면 시작을 실패시킨다. 이후 reload에서
  같은 일이 발생하면 기존 정상 구성을 유지한다. 캡처 자원 재설정은 초기 범위에서 재시작이 필요하다.

L7 기능이 늘어도 GSO 설정이나 checksum 검증 정책을 몰래 바꾸지 않는다. 향후 checksum을
검증한다면 offload로 아직 계산되지 않은 값을 손상 패킷으로 오인하지 않도록 metadata도 확인한다.

### 5.3 누가 데이터를 소유하는가

| 경계 | 넘기는 데이터 | 유효기간·소유권 |
| --- | --- | --- |
| PacketSource → decoder | 실제 수신 bytes와 길이·방향·시각·잘림 상태 | packet callback 안에서만 유효한 읽기 전용 view |
| decoder → 즉시 L7 parser | 검증된 payload 범위 | 같은 callback 안에서만 읽음 |
| TCP reassembly | 보관이 필요한 segment bytes | 재조립 저장소가 상한 안에서 복사·소유 |
| parser → Flow/AI/event | 필요한 요약 필드 | 자체 소유 값으로 저장. 수신 버퍼 pointer를 보관하지 않음 |

잘림·형식 오류 때문에 L7 분석을 생략하면 원인을 카운터와 빈도 제한 이벤트로 남긴다.
패킷 ID와 L3 정보를 정상적으로 읽을 수 있으면 기존 whitelist·BlockList·가능한 L3/L4 Rule을
적용하고, 분석 불가 자체만으로 새 차단을 만들지 않는다. netlink message가 손상돼 packet ID조차
모르면 verdict를 보장할 수 없다. 이 경우는 단순한 “L7 생략”이 아니라 캡처 오류로 보고한다.

## 6. fail-open이라고 부를 수 있는 범위

| 상황 | 현재 코드 기준 동작 | 해석 |
| --- | --- | --- |
| Python AI 장애·AI 요청 큐 포화 | 새 AI 차단 없이 Rule·기존 차단 지속 | AI 경로 fail-open |
| NFQUEUE 수신 프로그램 없음 | `--queue-bypass`에 따라 해당 큐로 보내지 않고 진행 | 미실행·종료 후 신규 패킷에 관한 동작 |
| 센서가 살아 있지만 verdict 처리가 멈춤 | 대기·지연·포화가 발생할 수 있음 | listener 부재와 다르므로 bypass 보장 없음 |
| 커널 NFQUEUE가 가득 참 | `NFQA_CFG_F_FAIL_OPEN` 미설정으로 기본 DROP | 현재는 queue-full fail-open 아님 |
| netlink 수신 버퍼 손실·메시지 손상 | 손실·캡처 오류 발생 가능 | AI 큐 포화와 별도 측정해야 함 |

`--queue-bypass`의 범위는 [iptables 공식 설명](https://ipset.netfilter.org/iptables-extensions.man.html),
queue-full 플래그는 [libnetfilter_queue 공식 설명](https://www.netfilter.org/projects/libnetfilter_queue/doxygen/html/group__Queue.html)을 따른다.
센서가 큐 길이 10,240개를 요청한다는 사실과 그 크기가 실제 적용됐다는 사실도 구분한다.
현재 코드는 요청 실패 시 경고 후 기본값으로 계속하므로 실험 기록에는 적용값을 확인해 남긴다.

이번 보완은 포화 시 DROP을 ACCEPT로 바꾸지 않는다. 그렇게 바꾸려면 공격자가 포화로 검사를
우회할 위험과 정상 통신 가용성의 균형을 따로 결정하고 Linux VM에서 확인해야 한다.
센서 강제 종료 전 이미 대기하던 패킷의 전달이나, 다른 방화벽 규칙의 통과까지 보장하지 않는다.

## 7. 구현 때 확인할 수용 기준

아래는 앞으로 추가·실행할 검증 항목이지, 이번 문서 작업에서 통과한 테스트 결과가 아니다.

| 검증 입력 | 기대 결과 |
| --- | --- |
| 같은 원격 IP의 연결 A 이상 판정, 연결 B는 진행 중 | 적용 이후 A/B/새 연결 모두 inbound 차단. 이미 전달된 bytes는 그대로 |
| 이미 차단된 IP의 중복 AI 결과 | TTL 연장·신규 차단 팝업 없음 |
| 로컬 DNS Flow + 정상 설치된 호환 프로토콜 모델 | 기존 Flow 모델은 제외, 프로토콜 AI 이상은 알림만 |
| DNS 모델 없음 또는 미지원 origin | parser/Rule은 동작, AI는 제외 이유 기록, IP 자동 차단 없음 |
| 화이트리스트 DNS 서버의 악성 도메인 응답 | 관찰·적중 기록은 남지만 서버·응답 IP를 자동 차단하지 않음 |
| AI 응답 대기 중 whitelist 변경 | 결과 적용 시 현재 면제를 존중 |
| 128바이트보다 긴 DNS·잘린 DNS·잘린 PCAP | 정상 전체 입력만 분석 성공, 잘림은 누락 기록. 범위 밖 읽기 없음 |
| packet callback 종료 후 재조립·AI 처리 | 재사용된 수신 버퍼를 참조하지 않음 |
| AI 중지·센서 종료·센서 정지·NFQUEUE 포화 | 6장의 상황을 각각 분리해 실제 verdict·손실·지연 기록 |

Windows 문서·코드 검토는 NFQUEUE 동작 검증을 대신하지 않는다. 자동 테스트와 격리된 Linux VM
실험이 끝나기 전에는 확장 기능을 “구현·검증 완료”로 표시하지 않는다.

## 8. 이번 범위 밖의 다음 작업

기존 ML 오류·테스트·CI·학습 데이터 분할 검증은 다음 안정화 작업에서 다룬다. PCAP의 시간 진행과
EOF 처리, Rule action별 지속 범위, reload와 상태 수명, 프로토콜별 framing·재조립 제한은 각 단계의
구현 계획에서 별도로 구체화한다. 이 문서만으로 전체 확장 설계의 구현 준비가 끝났다고 보지 않는다.
