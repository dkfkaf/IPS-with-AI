## 0. 기본 원칙

**포맷(코드 생김새)은 도구에 맡기고, 사람은 판단이 필요한 것만 신경 쓴다.**

- 들여쓰기, 띄어쓰기, 줄바꿈 같은 포맷 규칙은 자동 포맷터(clang-format, ruff)가 처리한다. 외울 필요 없다.
- 사람이 지킬 것은 이름 짓기와 주석처럼 도구가 대신 못 하는 부분이다.
- C++은 Google C++ 스타일 가이드를, Python은 PEP 8을 기본으로 하되, 두 언어의 이름 규칙은 최대한 통일한다.

## 1. 이름 규칙 (사람이 지킴)

두 언어를 오갈 때 헷갈리지 않도록 공통 규칙으로 통일한다.

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| 변수, 함수 | snake_case | `flow_count`, `parse_packet()` |
| 클래스 | PascalCase | `PacketParser`, `FlowManager` |
| 상수 | 대문자 + 밑줄 | `DEFAULT_TTL`, `MAX_FLOWS` |
| 파일 이름 | snake_case | `flow_manager.cpp`, `detector.py` |
| (C++) 클래스 멤버 변수 | 뒤에 밑줄 | `blocklist_`, `flow_map_` |

> 참고: 상수는 원래 Google C++이 `kDefaultTtl` 형태를 쓰지만, Python과 통일하기 위해 `DEFAULT_TTL` 방식으로 맞춘다. 두 언어의 일관성을 우선한다.

이름 규칙은 자동 포맷터가 고쳐주지 않으므로 **직접 지켜야 한다.** (더 엄격하게 하려면 나중에 clang-tidy / ruff의 naming 검사를 켤 수 있다. 지금은 선택.)

## 2. 주석 규칙 (사람이 지킴)

- 주석은 "무엇을 하는지"가 아니라 **"왜 이렇게 했는지"** 를 적는다. 코드만 봐도 아는 건 굳이 주석 달지 않는다.
- 함수 위에는 그 함수가 무엇을 하고 무엇을 반환하는지 한두 줄로 적는다.
- TODO는 `// TODO: 내용` 형식으로 남겨 나중에 찾기 쉽게 한다.

```cpp
// 나쁜 예: 코드를 그대로 옮긴 주석
count = count + 1;  // count를 1 증가

// 좋은 예: 이유를 설명
// 재전송 패킷은 중복 카운트를 막기 위해 제외한다
if (!is_retransmission) {
  flow_count++;
}
```

## 3. C++ 포맷 (clang-format이 처리)

Google 스타일을 기본으로 한다. 아래 설정 파일을 프로젝트 루트에 두면 자동 적용된다.

**파일 이름: `.clang-format`** (프로젝트 최상위 폴더에 위치)

```yaml
BasedOnStyle: Google
IndentWidth: 4
ColumnLimit: 100
```

- `BasedOnStyle: Google` — Google C++ 스타일의 포맷 규칙을 전부 가져온다.
- `IndentWidth: 4` — 들여쓰기 4칸. (Google 기본은 2칸이지만, 초보자 가독성을 위해 4칸으로 조정. 원하면 2로 바꿔도 됨.)
- `ColumnLimit: 100` — 한 줄 최대 100자. (Google 기본은 80자.)

### 사용법

터미널에서 파일 하나를 정리:
```bash
clang-format -i flow_manager.cpp
```
(`-i`는 파일을 직접 고친다는 뜻. 없으면 결과만 화면에 출력.)

VS Code를 쓴다면 C/C++ 확장을 설치하고 "저장 시 자동 포맷(Format On Save)"을 켜두면, 저장할 때마다 알아서 정리된다. 이게 제일 편하다.

## 4. Python 포맷 (ruff가 처리)

PEP 8을 기본으로 하고, `ruff`로 포맷과 간단한 검사를 자동화한다. ruff는 포맷터와 린터(코드 문제 검사기)를 겸한다.

**파일 이름: `ruff.toml`** (프로젝트 루트 또는 Python 폴더에 위치)

```toml
line-length = 100

[lint]
# E,W = PEP8 스타일 / F = 오류 검사 / I = import 정렬 / N = 이름 규칙 검사
select = ["E", "W", "F", "I", "N"]
```

### 사용법

```bash
# 포맷 자동 정리
ruff format detector.py

# 코드 문제 검사 (이름 규칙 위반 등도 잡아줌)
ruff check detector.py
```

`N`(pep8-naming)을 켜뒀기 때문에, 1번의 이름 규칙을 어기면 `ruff check`가 알려준다. 두 언어 이름 통일을 자동으로 도와주는 셈이다.

## 5. 기타 공통 규칙

- **한 파일에 한 가지 역할.** 예: 패킷 파싱은 `packet_parser`, 플로우 관리는 `flow_manager`로 파일을 나눈다. 파일 하나에 모든 걸 몰아넣지 않는다.
- **매직 넘버 금지.** 코드 중간에 `600` 같은 숫자를 직접 쓰지 말고 `DEFAULT_TTL = 600`처럼 상수로 이름을 붙인다. 나중에 값을 바꿀 때도 한 곳만 고치면 된다.
  - 단, **기계적으로 적용하지 않는다.** 상수의 이득은 ① 숫자에 의미를 붙이고 ② 여러 곳의 같은 값을 한 곳에서 고치게 하는 것이다. 이 이득이 없는 곳 — 사용처가 하나뿐이고 의미가 주석·문맥으로 충분한 값 — 은 리터럴 + 주석으로 둔다.
    - 상수로 만든다: 큐 번호처럼 **두 곳 이상이 일치해야 하는 값**(바인딩 + 안내 로그), 숫자만 봐서는 뜻을 모르는 값.
    - 리터럴 + 주석으로 둔다: `char line[64]`처럼 한 곳에서만 쓰이고 `sizeof`로 크기가 자동으로 따라가는 지역 버퍼 크기.
- **들여쓰기 수준은 얕게.** if 안에 if 안에 for... 처럼 깊게 중첩되면 함수로 분리하는 걸 고려한다.

## 6. 리팩토링

리팩토링은 **동작(기능)은 그대로 두고 코드 구조만 더 깔끔하게 바꾸는 것**이다. 미리 상세한 규칙을 정하기보다, "언제 하는가"와 "안전하게 하는 법"을 기준으로 삼는다.

### 6.1 언제 리팩토링하는가 (신호)

- **코드를 1차로 완성한 직후 (항상 수행)** — 동작하는 첫 버전이 나오면, 다음 기능으로 넘어가기 전에 **단순화 검토**를 한 차례 거친다. 볼 것: 중복·불필요한 상태, 형식적 상수(5장 매직 넘버 기준 참고), 숨길 상태도 없는데 class로 감싼 과잉 구조, 더 단순한 표준 도구로 대체 가능한 코드. "동작하게 만들기"와 "깔끔하게 만들기"를 한 번에 하지 않는다 — 커밋도 분리한다(6.2).
- **같은 코드를 세 번째 반복할 때** — 두 번까지는 넘어가도 세 번째면 함수로 뺀다 (Rule of Three). 예: 패킷에서 IP 뽑는 코드가 반복되면 `extract_ip()`로 분리.
- **함수가 화면을 넘어갈 때** (대략 50줄 이상) — 한 함수가 너무 많은 일을 하는 신호. 단계별로 쪼갠다. 예: NFQUEUE 콜백이 파싱·조립·검사·판정을 다 떠안으면 각각 별도 함수로.
- **중첩이 깊어질 때** — if/for가 3단계 이상 겹치면 함수 분리를 고려.

### 6.2 안전하게 하는 법

리팩토링의 가장 큰 위험은 구조를 바꾸다 기능을 망가뜨리는 것이다. 아래 수칙으로 방지한다.

- **Git 커밋을 분리한다.** 기능 추가 커밋과 리팩토링 커밋을 섞지 않는다. 그래야 문제가 생겼을 때 리팩토링 커밋만 되돌릴 수 있다.
- **리팩토링 전후로 동작을 확인한다.** 단위 테스트를 도입하기 전까지는 수동 테스트로 대체한다. 리팩토링 전에 프로그램을 돌려 정상 동작을 확인해두고, 리팩토링 후 다시 돌려 동일하게 동작하는지 비교한다.
- **한 번에 하나씩.** 여러 곳을 동시에 뜯어고치지 말고, 작은 단위로 바꾸고 확인하기를 반복한다.

### 6.3 향후

화이트리스트·TTL 등 핵심 로직이 복잡해지면 **Google Test로 단위 테스트를 도입**한다. 테스트가 있으면 리팩토링 후 즉시 기능 정상 여부를 확인할 수 있어, 수동 테스트보다 훨씬 안전하고 빠르다.

## 7. 객체 지향 설계 원칙 (주로 C++)

미리 규칙을 맞추기보다, 필요한 곳에 자연스럽게 적용한다. 아래 원칙들은 SOLID 원칙 중 본 프로젝트에서 실제로 쓰는 두 가지(S·O)와 연결된다.

### 7.1 캡슐화 — SOLID의 S (단일 책임)

**데이터를 클래스 안에 숨기고, 정해진 함수(통로)로만 건드리게 한다.** 관련된 데이터가 항상 짝을 맞춰야 할 때 특히 중요하다. 클래스 하나가 자기 데이터와 그 관리 책임만 지도록 하는 것이 SOLID의 단일 책임 원칙(S)이다.

- 내부 자료구조는 `private`, 바깥에서 쓸 동작만 `public`으로 연다.
- 통로는 "의미 있는 동작" 단위로만 연다. private 변수마다 get/set을 기계적으로 만들지 않는다 (캡슐화의 취지가 사라진다).
- **class는 숨길 것이 있을 때만 쓴다.** 숨길 내부 상태나 지켜야 할 불변식이 없는 타입 — 수동적 데이터 묶음(`FiveTuple`)이나 상태 없는 기능 묶음(`PacketParser`) — 은 `struct`로 둔다. struct/class의 기능 차이는 기본 접근 제한자뿐이므로, 이 구분은 "이 타입은 캡슐화 대상인가"를 읽는 사람에게 알리는 신호다. 나중에 상태가 생기면 그때 class로 바꾼다.

적용 대상:

| 클래스 | 숨기는 것 | 여는 통로(예) |
| --- | --- | --- |
| `BlockList` | map + min-heap (항상 함께 갱신돼야 함) | `Block()`, `IsBlocked()`, `CleanupExpired()` |
| `FlowManager` | 플로우 저장 자료구조 | `AddPacket()`, `GetFlow()` |
| `Whitelist` | 설정 파일에서 읽은 IP 목록 | `IsWhitelisted()` |

```cpp
class BlockList {
 public:
  void Block(uint32_t ip, int ttl_seconds);   // 차단 추가 (map+heap 동시 갱신)
  bool IsBlocked(uint32_t ip);                 // 차단 여부 확인
  void CleanupExpired();                       // 만료된 항목 정리

 private:
  std::unordered_map<uint32_t, TimePoint> block_map_;   // IP → 만료 시각
  std::priority_queue<...> expiry_heap_;                // 만료 순 정렬
};
```

`block_map_`과 `expiry_heap_`이 `private`이라 바깥에서 직접 접근할 수 없다. 반드시 `Block()`을 거치므로 두 자료구조가 어긋날 일이 없다.

### 7.1.1 좋은 코드가 갖추는 것

잘 짜인 코드에서 반복적으로 나타나는 특징들이다. 이름 규칙(1번)은 우리 표준(snake_case)을 그대로 따르되, 아래 정신을 지향한다.

- **자원은 짝을 맞춰 관리한다.** 여는 함수와 닫는 함수, 할당과 해제가 명확히 대응되게 한다. 한쪽만 있으면 자원 누수나 오류의 원인이 된다.

```cpp
bool BlockList::open() {
  // ... 자원 할당
}
bool BlockList::close() {
  // open()에서 할당한 자원을 여기서 정확히 대응 해제
}
```

- **에러 처리를 일관되게 한다.** 각 단계마다 실패를 확인하고, 통일된 방식으로 로그를 남긴 뒤 실패를 반환한다. 실패 경로가 예측 가능해진다.

```cpp
bool FlowManager::init() {
  if (!load_config()) {
    LOG(ERROR) << "설정 로드 실패";   // glog로 통일된 에러 기록
    return false;
  }
  return true;
}
```

- **한 함수는 한 가지 일만 한다.** "열기", "검사", "결과 알리기"를 각각 다른 함수로 나눈다. 이것이 단일 책임(SOLID의 S)이 함수 단위로 나타난 모습이다.
- **자원 관리는 가능하면 스마트 포인터를 쓴다.** C 스타일의 `malloc`/`free`보다 C++의 `std::unique_ptr` 등을 우선한다. 소멸 시 자동 해제되어 짝맞춤 실수를 줄인다.

> 참고: 위 특징들은 잘 짜인 기존 C++ 코드에서 배운 것을 본 프로젝트의 컨벤션(snake_case, glog, 스마트 포인터)에 맞춰 다시 정리한 것이다. 좋은 코드라도 다른 프로젝트의 이름 규칙을 그대로 섞으면 일관성이 깨지므로, 정신만 취하고 표기는 우리 규칙을 따른다.

### 7.2 디자인 패턴 — Strategy는 SOLID의 O (개방-폐쇄)

패턴은 미리 정해놓고 코드를 맞추는 게 아니라, 문제가 생겼을 때 꺼내 쓰는 도구다. 억지로 넣으면 과잉 설계가 된다. 우리 프로젝트에 자연스럽게 맞는 것만 적용한다.

| 위치 | 패턴 | 도구 | 도입 시점 |
| --- | --- | --- | --- |
| C++ Rule 검사 | Strategy | 추상 클래스 (순수 가상 함수) | Rule을 여러 개 만들 때 |
| Qt 대시보드 | Observer | signal-slot (Qt 내장) | 대시보드 만들 때 |
| Python AI 엔진 | Strategy | 추상 클래스 | 랜덤포레스트 추가 시 |

**Strategy (Rule 검사)** — 여러 탐지 규칙을 갈아끼우거나 추가할 수 있게 한다. `Rule` 추상 클래스를 두고 각 규칙을 자식으로 구현하면, 새 규칙을 추가할 때 기존 코드를 건드리지 않고 클래스만 붙이면 된다. 기능 추가는 새 코드로, 기존 코드는 그대로 두는 이것이 SOLID의 개방-폐쇄 원칙(O)이다.

```cpp
class Rule {
 public:
  virtual ~Rule() = default;
  virtual bool IsMatch(const Flow& flow) = 0;   // 자식이 각자 구현
};

class PortScanRule : public Rule {
 public:
  bool IsMatch(const Flow& flow) override { /* 포트 스캔 판정 */ }
};
```

**Observer (대시보드)** — 차단 같은 사건이 발생하면 대시보드가 받아 화면을 갱신한다. Qt의 signal-slot이 이 패턴을 언어 차원에서 지원하므로, Qt를 쓰는 것만으로 자연스럽게 적용된다.

### 7.3 과잉 설계 경계

- 패턴이나 캡슐화를 "써야 좋은 것"으로 여겨 억지로 넣지 않는다.
- SOLID도 5개를 모두 형식적으로 맞추려 하지 않는다. 본 프로젝트에서 실제로 의미 있는 것은 S(단일 책임)와 O(개방-폐쇄)이며, 나머지(L·I·D)는 상속 구조가 복잡해질 때 비로소 필요해진다.
- 지금 필요 없는 구조는 만들지 않는다. 예: 프로토콜별 파서 Factory는 5-튜플만 뽑는 현 단계엔 불필요.
- 1단계(패킷 수신·파싱)에서는 위 패턴 대부분이 필요 없다. 해당 기능을 실제로 만들 때 도입한다.
